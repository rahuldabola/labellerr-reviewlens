It also finds real mistakes in COCO itself

I ran ReviewLens on the original COCO labels (no noise injected) and eyeballed the 20 highest-scoring flags: ~10 look like genuine labelling errors (unlabelled pedestrians, spectators and a skier; a car cut off at the image edge; small cars labelled "truck"; a bowl labelled "cup"), ~4 are genuinely ambiguous (a cake in a pan labelled "bowl", a terracotta vase vs. cup), exactly the cases a project guideline should settle, and ~6 are model false alarms (a person on a bus poster, a ball basket seen as a chair). That also explains part of the "precision" gap above: some flags that miss the answer key are real errors in COCO. This is one person's thumbnail-level judgement, not a labelled study.

Caveats I would not hide from a customer

  • Injected errors are a simulation. Real annotator mistakes are subtler (borderline boxes, guideline misreads), so these numbers are an upper bound on ease and a lower bound on usefulness for gross errors.
  • The detector (YOLO11m, COCO-pretrained) is in-domain here. On a customer's niche domain you would use their own checkpoint from the active-learning loop; the self-calibration downweights classes the model is bad at, but a weak model still means weaker triage.
  • About half of injected "missing labels" are not flagged: mostly tiny or occluded objects the model cannot see either.
  • Labellerr round-trip code is written against the official SDK source but has not been run against a live workspace yet.
